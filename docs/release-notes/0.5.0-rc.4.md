# v0.5.0-rc.4: Scoped Authorization

September 8, 2026. **Prerelease, not stable.**

## Changes

- API keys are distinct principals, with explicit permissions, creator ownership
  and bounded expiry. They no longer impersonate a human administrator.
- Members manage their own keys. Human admins manage organization keys, members
  and settings. Keys cannot delegate keys or administer members/settings.
- All protected API routes enforce role/scope policy. Sensitive Vault, registry
  and audit automation requires explicit admin-granted scopes.
- Keycloak access tokens require a valid API audience, issuer, subject, signature
  and expiry. ID tokens and client `azp` alone are insufficient.
- Terminal tickets bind the real principal; active terminals and command-output
  streams recheck authorization. Revocation disconnects observers without
  cancelling detached commands or deleting sandbox/workspace resources.
- The dashboard adds permission and expiry selection, owner-aware key lists,
  one-time copying and revocation confirmation. Member settings are read-only.
- Public documentation adds the authorization concept, permissions matrix,
  rotation guidance, security limits and ordered operator upgrade instructions.
  The redesigned documentation experience is included in this matched release.

## Upgrade Before Deploying

1. Back up PostgreSQL and export the existing Keycloak client configuration.
   Inventory legacy keys and preserve a human administrator login.
2. Add the `harakiri-api` audience to access tokens for each authorized Keycloak
   client. Keep ID-token mapping disabled and public redirect URLs unchanged.
   Existing realm imports do not update existing clients.
3. Obtain a fresh access token and verify its audience locally before upgrading.
4. Apply migration `037_authorization_principals.sql` using the normal migration
   runner; deploy the matching API, scheduler, builder and web/chart. Set
   `KEYCLOAK_AUDIENCE=harakiri-api`, `KEYCLOAK_SIGNING_ALGORITHMS=RS256`, and
   keep `AUTH_DEV_ALLOW=0` on public installations.
5. Verify admin/member workflows, issue scoped replacement keys, test real
   integrations, and then retire their legacy keys.

**Compatibility change:** pre-037 keys retain a runtime-only legacy profile and
their existing expiry, but lose implicit administrative access. Vault, registry
and audit management callers need explicitly scoped replacements. Only human
admins can manage unowned legacy keys. Existing terminal tickets must be renewed.
New keys expire after 90 days by default, with a maximum of 365 days.

An old API rollback restores weaker authorization; prefer forward recovery.
Do not disable audience checks or change public login to localhost as a workaround.
See [authorization and API keys](../authorization.md) for the full contract.

## Verification and Limits

Local implementation acceptance: 331 API tests with PostgreSQL, seven browser
tests, SDK/CLI dev-provider conformance, root build/typecheck/tests, OpenAPI,
documentation links, Vault boundary checks and Helm/install-config validation.
Live acceptance is recorded separately after deployment.

Keycloak JWTs are verified offline, so logout is not immediate revocation before
access-token expiry. Key revocation does not stop existing runtimes, erase copied
credentials or revoke independent preview-route tokens. Shared runtime write
access remains a substantial trust grant, not per-user sandbox isolation.

Clean restricted OpenShift storage acceptance, complete template architecture
checks, host recovery and coherent database/PVC recovery remain open. This
candidate does not claim to complete those gates.
