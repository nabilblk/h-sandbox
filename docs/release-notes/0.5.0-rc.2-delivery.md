## SDK and CLI Installation

**npm publishing is blocked by missing local authentication.** Registry checks
on September 7 show both `latest` tags still at `0.4.0`, with no `0.5.0-rc.2`
version or `next` tag. Do not use `npm install @h-sandbox/sdk@next` yet.
Configure publishing credentials privately, never in chat or tracked files.

For testing now, use the attached, matching packages together in a disposable
consumer directory. The CLI depends on the matching SDK; installing both in one
command avoids looking for the unpublished SDK version in npm.

```bash
mkdir harakiri-rc2-test
cd harakiri-rc2-test
gh release download v0.5.0-rc.2 --repo nabilblk/h-sandbox --pattern '*.tgz' --pattern 'SHA256SUMS'
shasum -a 256 -c SHA256SUMS
npm init -y
npm install ./h-sandbox-sdk-0.5.0-rc.2.tgz ./h-sandbox-cli-0.5.0-rc.2.tgz
./node_modules/.bin/harakiri --version
```

Set `HARAKIRI_API_URL=https://sb-api.harakiri.io` and supply an API key from your
workspace privately. Follow the [persistent workspace tutorial](../persistent-workspaces.md).
The exact packages above were installed together and exercised against the live
provider, not only imported from source.

After publishing authorization is restored, use a clean checkout of the exact
tag, publish SDK then CLI on `next`, and run the registry post-publish smoke.
Do not move `latest`, retag source or overwrite rc.1 artifacts.

## Deployment

The public k0s lab runs Helm release `harakiri`, namespace `harakiri`, revision
**22**, chart/app `0.5.0-rc.2`. API, scheduler, template builder and web use the
index digests above; the builder job image is pinned to the same API digest.
Revision 21 was the initial rc.2 rollout; revision 22 corrected its generated
builder job image coordinate. It did not replace release artifacts.

PostgreSQL, the template registry and running sandbox resources were preserved.
The CLI test sandbox survived the API/scheduler upgrade and accepted commands
afterward. Public origin port-forwards recovered automatically after replacement
pods; brief 502s occurred during handoff. This is not zero-downtime evidence.

Final public checks returned HTTP 200 for:

- [Dashboard](https://sb.harakiri.io/).
- [API health](https://sb-api.harakiri.io/health).
- [OIDC discovery](https://sb-auth.harakiri.io/realms/harakiri/.well-known/openid-configuration).

Public auth/API/web origins stay on these domains, not loopback. The tunnel is
the existing supervised `harakiri-dev`. The native workspace lab profile is
enabled with `local-path`, 1 GiB per workspace and 20 allocation slots per
organization. These lab values are not a customer storage recommendation.

## Known Gates

- **Renewal/scheduler defect:** a renewed test sandbox was terminated at its
  original idle schedule. `renewSandbox` advances the sandbox/provider expiry,
  but scheduler selection still uses the original `sandbox_schedules.run_at`.
  This behavior also exists in `v0.4.0`. Fix authoritative deadline/renewal
  coordination, add real PostgreSQL coverage and pass a beyond-original-deadline
  test before stable promotion. Use a sufficient initial TTL for bounded RC tests.
- [Template CI](https://github.com/nabilblk/h-sandbox/actions/runs/34109679290):
  11 of 12 architecture jobs passed. OpenCode amd64 arbitrary-UID runtime smoke
  timed out after 90 seconds; the manifest publication job correctly stayed
  skipped. Existing template tags/aliases remain unchanged.
- Fresh restricted OpenShift storage permission acceptance, host reboot/login
  recovery and coherent rollback validation remain open. The populated CRC
  namespace was intentionally not used for destructive reinstall testing.
- Archive retains storage and quota. Replay relies on provider log retention.
  No persistent-workspace snapshot/restore guarantee is offered.

## Backup and Recovery

Private PostgreSQL custom-format dumps and captured Helm/configuration values
exist under ignored `docs/artifacts/release-0.5.0-rc.1-private/` and
`docs/artifacts/release-0.5.0-rc.2-private/`. File permissions restrict credentials;
none are attached to the release. Both dump catalogs were checked with
`pg_restore --list`; a full restore drill was not performed.

The pre-migration backup is 457820 bytes, SHA-256
`67cca67a9b3af31096709069ebac176b742d198e080df0855eaf8e1a8ad5ca24`.
The pre-rc.2 backup is 469667 bytes, SHA-256
`c68f45fad25ccf822ed452a6bdc8ffa508032feabde244560fe676dcd3cd2e1c`.

Migration 035 is additive; do not run a destructive down-migration or blindly
roll back to 0.4.0 while workspace reservations exist. Restore compatible API and
scheduler together and follow the [workspace recovery procedure](../persistent-workspace-operations.md).
Database and PVC backups must refer to a coherent point. A database dump alone
does not back up project files. Local-path storage does not protect against node loss.
