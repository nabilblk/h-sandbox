## Deployment and Backup

The public k0s lab now runs Helm release/namespace `harakiri`, revision **25**,
chart/app version `0.5.0-rc.3`. API, scheduler and builder use the API index above;
the web and builder job image are also digest-pinned to the matching release.

Before upgrade, PostgreSQL was backed up in custom format: 477059 bytes, SHA-256
`de4c49b1ae9de8b44446c034e2b9aa214f27df8e491619cab2bd228762d8baa9`.
`pg_restore --list` validated the catalog. A full restore drill was not run.
The backup, captured Helm values and configuration are private and excluded from
Git/release assets under `docs/artifacts/release-0.5.0-rc.3-private/`.

The old scheduler was scaled to zero before migration 036. Revision 24 deployed
the matched images while holding the scheduler stopped; after API readiness,
revision 25 started the corrected scheduler. All four application deployments
are ready. Rendered resource inventory, application secrets and runtime settings
were compared; only intended image, release metadata and builder-job changes
were accepted. Existing PostgreSQL, registry and workspace storage were retained.

The supervised public API forward briefly returned 502 during pod handoff and
recovered automatically. The first smoke key request therefore failed and was
retried only after health stabilized. This is not zero-downtime evidence.

Do not drop migration 036 on rollback. The old scheduler restores the original
TTL defect; prefer forward recovery and follow [lease operations](../sandbox-lease-operations.md).
A database backup alone is not a PVC backup or coherent workspace restore proof.
