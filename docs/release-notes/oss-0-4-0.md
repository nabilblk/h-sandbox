# Harakiri Sandbox OSS 0.4.0 Release Candidate

Date: 2026-09-02
Last updated: 2026-09-03

This release candidate hardens Harakiri as an installable OSS sandbox control
plane on top of OpenSandbox. The focus is release trust: current runtime pins,
clear provider boundaries, repeatable Helm deployment, public SDK/CLI
conformance, OpenSandbox-native lifecycle persistence, and honest capability
reporting.

## Highlights

- OpenSandbox runtime pins are upgraded to the `0.2.x`/`1.1.x` generation:
  server `v0.2.3`, chart `0.2.2`, controller `v0.2.0`, execd `v1.1.0`, egress
  `v1.1.7`, ingress `v1.0.10`, and image committer `v0.1.1`.
- Runtime behavior stays behind the `RuntimeProvider` interface. Normal sandbox
  commands, files, logs, metrics, routes, terminal attach, lifecycle, and egress
  do not use Harakiri-owned Kubernetes pod exec/log/filesystem shortcuts.
- OpenSandbox-native lifecycle persistence is now exposed end to end: pause,
  resume, snapshot create/list/get/delete, and restore from a Harakiri
  `snp_...` snapshot ID.
- Helm is now the authoritative Harakiri deployment model for k0s and operator
  installs. The old raw kustomize Harakiri app manifests are no longer the
  default deploy path.
- Hosted web runtime config is mounted by the Helm chart and exposes only public
  web/API/Keycloak URLs. Browser OIDC tests fail if `localhost` or `127.0.0.1`
  leaks into hosted auth/API requests.
- Runtime capability health reports `available`, `degraded`, `unavailable`, and
  `unsupported` states for lifecycle, commands, terminal attach, files, logs,
  metrics, routes, and egress.
- SDK and CLI conformance can run without Kubernetes through
  `pnpm conformance:dev`, and strict conformance still runs against the real
  OpenSandbox-backed k0s deployment.
- CLI terminal attach now waits for the provider PTY to be ready before
  accepting input, fixing dropped commands in piped `harakiri attach --no-raw`
  usage.

## Supported Capabilities

- Sandbox create, list, get, renew, kill, readiness wait, and TTL scheduling.
- Capability-gated pause/resume, snapshot create/list/get/delete, and
  create-from-snapshot through API, SDK, CLI, and dashboard.
- Blocking command runs, tracked detached commands, persistent command sessions,
  and interactive terminal attach.
- Filesystem list/read/write/mkdir/remove/rename plus artifact upload/download.
- Runtime logs and metrics through provider-owned endpoints with explicit
  degraded states when provider data is unavailable.
- Public and token-protected sandbox routes through the OpenSandbox ingress
  gateway.
- Egress modes, presets, custom allow/deny rules, and runtime egress tests where
  OpenSandbox egress sidecars are available.
- Template catalog usage, Dockerfile/image template records, build metadata, and
  Open Agents pilot template documentation.
- Keycloak OIDC browser sign-in/logout and API key based CLI/SDK auth.

## Known Limits

- OpenShift one-namespace install docs are patch-free, but still need a clean
  customer-style live verification pass before being treated as final operator
  collateral.
- Template image publishing is documented but not yet automated as a
  first-class release workflow. `open-agents-dev` has validated image
  coordinates, but external handoff should pin an explicit tag or digest until
  the template release pipeline exists.
- Long-term volumes, Python SDK, MCP server, and framework-specific adapters
  remain follow-up integration work.
- Snapshot fork/branch workflows are not yet a high-level product surface.
  Snapshot create/delete/restore is available, but lineage, branch naming, and
  compare/promote UX remain follow-up Phase 2 work.

## Upgrade Notes

- Use the Helm chart for Harakiri app deployment. The raw `infra/k8s`
  kustomization now contains local dependencies and OpenSandbox helpers, not the
  authoritative Harakiri application deployment.
- Set public web/API/Keycloak URLs through Helm values. Do not patch
  `/config.js` after deployment.
- Keep OpenSandbox, Harakiri API, scheduler, and template-builder RBAC separate.
  Direct Kubernetes pod exec is not a normal runtime integration surface.
- For OpenShift environments that cannot grant the OpenSandbox egress sidecar
  requirements, use the restricted OpenShift values that avoid injecting the
  no-op open egress policy for open-network sandboxes.
- To enable OpenSandbox snapshot persistence in local k0s, configure a
  node-reachable snapshot registry. The validated local profile used
  `192.168.5.15:5000/harakiri/snapshots` plus a guarded containerd socket
  compatibility link for the pinned OpenSandbox controller image.
