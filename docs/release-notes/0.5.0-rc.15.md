# 0.5.0-rc.15: Standalone OpenShift Onboarding

Date: 2026-11-06. Developer preview for isolated client testing, not a stable
promotion or native OpenShift certification.

## Delivery Status

API/web images, the Helm chart and the TypeScript SDK/CLI preview are published.
The existing k0s lab is running rc.15 at Helm revision 52. The public OpenShift
guide and changelog are deployed. Consult the
[delivery receipt](0.5.0-rc.15-delivery.md) for exact digests and verification:
successful k0s delivery is not native OpenShift qualification.

## What Changes

- A standalone, dependency-free configuration kit produces reviewable Helm
  values, runtime resources, network policies and a qualification receipt.
  It requires explicit HTTPS origins, existing Secret references and image
  digests, refuses overwrite and does not contact a cluster during generation.
- The control-plane chart supports digest-pinned API/web images, declarative
  OpenShift Routes, read-only filesystems with bounded temporary storage and
  private CA mounts. Restricted validation rejects unsafe combinations rather
  than adding SCC permissions. Ordinary chart defaults retain their behavior.
- Provider-neutral `RUNTIME_DISABLED_FEATURES` makes operator restrictions
  visible in discovery and rejects unsupported operations before new effects.
  Queued provisioning rechecks policy before dispatch and releases an unused
  capacity reservation. Historical inspection and cleanup remain available.
- The restricted profile disables mutable domain egress, runtime Vault
  injection, pause/resume, snapshots/restore, persistent workspaces and
  in-cluster Dockerfile builds. Container isolation and cluster NetworkPolicy
  are not a microVM or a replacement for domain-based egress enforcement.
- A bounded, read-only preflight requires explicit kubeconfig/context. An
  opt-in SDK smoke checks capability denial, readiness, non-root execution,
  a 1 MiB binary round trip and confirmed cleanup of only its own sandbox.
- A first-class public OpenShift guide covers platform handoff, identity,
  Secret ownership, registry trust, installation, diagnostics and recovery.
  No customer application or optional integration is part of this installation.

The SDK classifies `runtime_feature_unavailable` as an unsupported capability,
not a transient error. Existing clients retain HTTP 501 semantics.

## Operator Boundaries

PostgreSQL, Keycloak, registry trust, namespace quotas and runtime CRD/RBAC
approval are platform prerequisites. Runtime controllers still need their
reviewed cluster-scoped permissions; one application namespace does not mean
namespace-only privileges. No default SCC is changed.

Use this restricted profile for a fresh isolated installation, not an in-place
downgrade of workloads using Vault, snapshots or persistent storage. Web/API
Routes use edge TLS; internal hops remain HTTP. Sandbox egress is DNS-only by
default, with explicitly approved CIDRs for HTTPS. Review additive policies and
actual DNS/router topology with the platform team.

## Upgrade And Rollback

No database migration is added relative to rc.14. Back up operator values,
database, encryption keys and retained storage; preserve public OIDC origins,
Secrets and existing capability settings. Upgrade API/scheduler/template worker
together with the matching chart and web image. Do not use the legacy development
installer against the public lab or a client cluster.

The new restriction guard is absent from rc.14. Do not roll a restricted
installation back to that API while leaving restricted values in place: the
older API would ignore the new configuration. A previous chart/image pair may
be used for an unrestricted lab rollback only after reviewing configuration and
data compatibility. Image rollback never reverses a database migration.

## Qualification And Client Handoff

Local tests cover configuration validation, unsafe Helm overrides, deployment
policy, queued admission cleanup, SDK smoke ownership and documentation layout.
CI and registry verification are recorded separately in the delivery receipt.
Neither those checks nor k0s deployment qualifies OpenShift SCC admission,
arbitrary-UID execution, CRI-O behavior or network isolation.

The client should use an approved isolated target, follow the
[installation guide](../install-openshift.md) and return the sanitized
[qualification checklist](../openshift-qualification.md). Record exact cluster,
architecture, SCC, image/chart digests and observed failures. Do not send raw
Secrets, tokens, kubeconfigs or sensitive application logs.
