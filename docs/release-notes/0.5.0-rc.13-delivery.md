## Existing k0s Lab

The explicit lab kubeconfig/context targeted only the existing k0s cluster.
The ambient customer/OpenShift context was not used. A private capture retained
release-owned resources and Helm values before a single guarded upgrade.

- Helm release `harakiri`, namespace `harakiri`, revision **49 to 50**.
- Installed chart/appVersion remains **0.5.0-rc.10**; API, scheduler,
  template-builder and web now use verified **rc.13 image digests**. This is an
  image deployment, not an rc.13 chart installation receipt.
- The published rc.13 chart differs from the retained rc.10 archive only in
  Chart.yaml version/appVersion. Keeping the installed chart avoided unrelated
  metadata/checksum changes in this lab.
- Helm rendering and server-side admission previews permitted only the four
  images, builder-job image reference and independently reproduced shared-config
  checksums. Live resources matched the approved result.
- All four deployments were ready with the expected running image IDs.
  Twenty owned resources, 356 protected resource fingerprints and all 13
  unrelated active pod identities/readiness/restart counts were verified.
- Operator values, credentials, public OIDC configuration, storage and unrelated
  workloads were preserved. No provider, cluster or tunnel restart was performed.
- No new migration exists. The existing `AUTO_MIGRATE=1` startup checker was
  preserved, and migration source was unchanged. No database dump, restore or
  queried migration ledger is claimed. Helm hooks were skipped.

The upgrade used rollback-on-failure and readiness waiting. This does not qualify
an arbitrary cross-version database rollback or promise zero downtime.
