# 0.5.0-rc.13: Sandbox Workbench

October 16, 2026. Published core release candidate. SDK and CLI are available on
npm `next`; stable `latest` remains `0.4.0`. The API/web images and Helm chart are
published, and the public k0s lab runs the verified rc.13 images. See the
[delivery record](0.5.0-rc.13-delivery.md) for exact identities, qualification,
deployment boundaries and the resolved npm metadata propagation delay.

## What Changes

- Overview separates execution readiness from lifecycle status and shows
  expiry, execution-slot state, template, working directory, workspace and
  runtime capabilities. Readiness is not application or model-provider health.
- Terminal is a lazy-loaded xterm.js PTY with ANSI, raw keys, resize, interrupt,
  disconnect and explicit reconnect through the existing one-time authorized
  ticket contract. Opening Overview does not start a shell. Reconnect does not
  guarantee recovery of an earlier shell; OSC clipboard writes and hyperlink
  escapes are disabled. Scrollback and queued output remain bounded.
- Filesystem provides inert UTF-8 previews up to 256 KiB, destination-confirmed
  uploads and downloads with byte-size and SHA-256 checks. Browser transfers
  are buffered, limited to 16 MiB decoded or the lower server limit; directory
  display is capped at 300 entries. Cancellation may leave an accepted remote
  write. This is not an editor, deletion UI, streaming transfer or atomic
  create-only upload.
- Selected commands refresh by ID even outside the recent-command list.
  Completion refreshes canonical status and exit code, or `finishReason` when
  no exit code exists. Refresh and output following never resubmit commands;
  closing the viewer does not terminate work.
- File refresh reloads a selected preview even when the file name and size are
  unchanged. A successful listing removes previews for files deleted elsewhere;
  failed listings hide stale preview contents. These review fixes are included
  in the candidate, not deferred follow-up work.
- Logs support text, source and level/event filters, manual refresh and serial
  three-second follow while visible. The display retains at most 1,000 whole
  entries and 500,000 characters; failed refreshes label the retained snapshot.
  Provider-retained snapshots are not a durable replay stream.
- Metrics refresh serially every five seconds and distinguish provider
  observation time from fetch time. Unmeasured fields are unavailable, not zero;
  failed reads do not display cached values as current observations.
- CLI `doctor [id]` performs read-only configuration/capacity checks and optional
  execution-readiness checks. `status --check` reports readiness and exits 1
  when not ready. `--web-url` or `HARAKIRI_WEB_URL` adds an explicit dashboard
  link without guessing an origin or opening a browser. Ordinary `status`
  behavior without the new options is unchanged.
- Cancelling a web request interrupts its initial or forced token-refresh wait
  without cancelling shared authentication for other callers. A late refresh
  does not send the cancelled request.

## Metrics Contract

`GET /v1/sandboxes/:id/metrics` now returns
`503 sandbox_metrics_unavailable` when the provider cannot supply current
metrics. It no longer synthesizes an observation from persisted CPU/memory
values. An absent sandbox in the caller's organization still returns 404.
Callers must handle unavailable observations instead of assuming a successful
response with cached values.

Optional `availableFields` identifies measured fields; optional `observedAt`
records provider time, with `null` meaning unknown. OpenSandbox currently
supplies CPU/memory, not disk I/O or network counters. Legacy numeric zeros
remain in the wire shape for compatibility, but are not measurements when
absent from `availableFields`. An unknown timestamp produces no time-series
sample. A single observation is not historical resource usage.

New UI/CLI readers conservatively treat older responses without metadata as
CPU/memory only. Upgrade API and web together: a new client cannot eliminate
an older API's persisted-value fallback. Historical usage collection and its
existing migrations are separate from this change.

## Included Provider Fix

Core rc.13 includes the OpenSandbox file-transfer correction first delivered
in the API-only maintenance release `api-2026-10-02.1`. Uploads use the native
multipart endpoint and downloads use the native binary endpoint, avoiding the
old shell argument-size and chunked-base64 failure modes. The public API still
uses bounded JSON/base64; this is not public large-file streaming.

The [maintenance delivery receipt](2026-10-02-provider-files-delivery.md) and
[provider-fix record](provider-file-transfer.md) describe that earlier work.
Their native results do not qualify the full rc.13 Workbench candidate.

## Versions And Upgrade

The root, API, web, shared, SDK and CLI manifests, plus Harakiri chart `version`
and `appVersion`, align at `0.5.0-rc.13`. Use matching core API, scheduler,
template-builder, web and chart artifacts for an rc.13 installation.

Install the exact published core clients:

```sh
npm install --save-exact @h-sandbox/sdk@0.5.0-rc.13
npm install --global @h-sandbox/cli@0.5.0-rc.13
harakiri --version
```

Anonymous installation of both published packages passed. The general public
SDK examples pin rc.13, and their version is checked against
the SDK manifest used to build the archive. Two deliberate documentation
exceptions remain:

- The TypeScript Deep Agents adapter stays `0.1.0-rc.2`, with exactly SDK
  `0.5.0-rc.12` and Deep Agents `1.14.0`. Its page and examples retain those
  peers. This core release does not claim adapter compatibility with SDK rc.13.
- The Kubernetes installation guide retains its qualified rc.9 bootstrap and
  pinned rc.10 install/upgrade artifacts and checksums. It is historical
  installation evidence, not a fresh rc.13 receipt.

Python SDK/adapter versions and all independent integration pins are unchanged.
No adapter publication or stable-channel promotion is part of this core release.

**No new database migration is required.** Earlier release migrations still
apply when upgrading an older installation; no schema downgrade or arbitrary
cross-release rollback is qualified here. Preserve operator-owned values,
origins, secrets, storage, keys and existing workloads. Feature descriptions
are not instructions to deploy over a running environment.
