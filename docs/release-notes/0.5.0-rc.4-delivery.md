## Ordered Deployment

1. Captured Helm revision 26, configuration, the Keycloak client/realm and an
   inventory of eight active legacy keys and four retained workspaces privately.
2. Added the `harakiri-api-audience` mapper to the live `harakiri-web` client.
   A fresh human access token contained `aud=harakiri-api` and the public
   `https://sb-auth.harakiri.io/realms/harakiri` issuer; the old API accepted it.
   Other client settings and SMTP were unchanged.
3. Backed up PostgreSQL in custom format: 480422 bytes, SHA-256
   `31444c272857af6f8ae00a3017990f52e4e3e0a8ed44df1298d0ca19497c2c4f`.
   `pg_restore --list` validated the catalog. No full restore drill was performed.
4. A structured server-side Helm render comparison allowed only release images,
   release metadata, the builder-job image and the two JWT validation settings.
   The existing migration runner applied 037 before the API listened;
   `AUTO_MIGRATE=1`, `SEED_ON_BOOT=0` were preserved.
5. Helm revision **27** deployed matched API, scheduler, builder and web images.
   All four became ready; application secrets, public runtime URLs and retained
   workspace records were unchanged.
6. Live browser testing discovered a populated-list mobile overflow missed by
   the original empty-list fixtures. A web-only CI release corrected it without
   republishing the API/chart/npm artifacts. A second structured comparison
   permitted exactly one web image change. Revision **28** is the final deployed
   state, with the corrected web digest pinned above.

During the first rollout, 90 public health samples captured one web 502 and one
API 502 around 16:42:35 UTC as supervised port-forwards changed pods. They
recovered automatically. This is not a zero-downtime claim. Browser acceptance
was rerun after the web handoff and full reload, not against stale SPA assets.

No existing sandbox/workspace storage, provider deployment, template alias,
BackgroundAgent installation or OpenShift namespace was redeployed or deleted.

### Actual Public Runtime

Using npm-installed rc.4 SDK/CLI, real Keycloak and a native OpenSandbox runtime:

- Valid human JWT accepted; missing credentials and ID token rejected with 401.
- Member settings writes, member administration and excessive key scopes denied.
  Members could create/list their own keys but not revoke another creator's key.
- Read-only key could list sandboxes but not create them or read audit data.
  Even an all-scope key could not impersonate a human, delegate keys or write
  settings. Explicit sensitive scopes enabled registry/audit reads.
- Sandbox `sbx_9FsaT1daey` executed the registry-installed CLI command and returned
  valid JSON output/completion events. Its owner was the key principal with a
  null human owner, not a borrowed administrator.
- Single-use terminal ticket replay was rejected. Revocation closed the active

- The already-started detached command still completed successfully through a

- The test runtime was terminated and its native pod disappeared.

## Registry Incident and Remaining Gates

Harbor's read-only health reported healthy while uploads returned HTTP 500.
The error body identified filesystem `mkdir` error 28 (no space), not a project
quota or bad credential. The first API publication and eight template uploads
failed for that reason; the application stayed on its prior deployment.

Dry-run GC 1288 estimated 9618 MB reclaimable. GC 1289 then reported **9573 MB**
recovered with `delete_untagged=false`, `delete_tag=false` and one worker. No
artifact/tag deletion policy or recurring schedule was added. An empty upload
returned 202 and was cancelled; both previous deployment images remained
pullable. This followed Harbor's separation between unreferenced-blob collection
and optional artifact deletion. [Harbor garbage-collection documentation](https://goharbor.io/docs/main/administration/garbage-collection/).

The separate [template workflow](https://github.com/nabilblk/h-sandbox/actions/runs/34250836054)
was not broadly retried after recovery: four architecture jobs passed, eight
uploads failed, and combined manifests were skipped. No template alias was
promoted. Storage/inode monitoring, reviewed retention/GC policy and template
capacity planning remain operational follow-ups, alongside unattended npm
trusted publishing, clean restricted OpenShift/storage acceptance and coherent
database/PVC recovery in the [delivery plan](../exec-plans/active/delivery-readiness-and-persistent-workspaces.md).

Keycloak logout is not immediate revocation of offline-verified JWTs before
expiry. Key revocation does not stop runtimes, retract copied credentials or
revoke independent preview-route tokens. See the public
[authorization guide](https://sb.harakiri.io/#docs/authorization).

## Cleanup and Recovery

All **12 dedicated test keys** were revoked and checked for rejection; the test
sandbox was terminated and the dedicated member removed from Keycloak and the
application. Historical audit records were retained. The eight original active
keys and four retained workspaces were preserved. The temporary file containing
test passwords/keys was removed. All four application deployments are ready at
revision 28; public web, API health and realm discovery return HTTP 200.

Private backups, deployment snapshots and browser evidence remain excluded from
Git under `docs/artifacts/release-0.5.0-rc.4-private/`. Publishing/login credentials
are not in source, release assets or screenshots of one-time key values.

Migration 037 is additive, but rolling back to the old API restores weaker
authorization. Prefer forward recovery and preserve the audience mapper. For
the web-only correction, revision 27 retains the original rc.4 UI while keeping
the stricter backend. A database backup is not a coherent database/PVC restore
proof, and no runtime storage rollback was attempted.
