# 0.5.0-rc.9: Execution Capacity and Cold-Start Readiness

September 11, 2026. Developer Preview candidate; stable npm `latest` remains
`0.4.0`. Matching API, web, chart, SDK and CLI target the `next` release track.
Publication and deployment receipts are recorded separately from source tests.

## Developer Changes

- Atomic organization execution admission reserves a slot before provider
  dispatch. Starting, stopping and uncertain work count until authoritative
  evidence permits release. CPU, memory, storage quotas and historical usage
  are not provided by this counter.
- `GET /v1/org/capacity`, SDK `client.capacity()` and CLI `harakiri capacity`
  expose reservations. Full organizations return a structured 409; unverified
  inventory returns 503. Create/resume retries retain their original intent key.
- `GET /v1/sandboxes/{id}/readiness` reports uncached execution health with
  `sandboxes:read`. The provider adapter checks its execution service, not a
  warm-up command or Kubernetes exec. Lifecycle `running` alone is insufficient.
- Default SDK/CLI creation and SDK waits require execution health before the
  first task. Async creation and exhausted HTTP wait budgets return an accepted
  ID; wait on that same ID. Cancellation stops the observer, not the sandbox.
- Onboarding does not submit the first command after a pending response; retry
  retains the creation key. File writes and commands are never automatically
  replayed to hide a readiness failure.

## Install and Upgrade

```bash
npm install --save-exact @h-sandbox/sdk@0.5.0-rc.9
npm install --global @h-sandbox/cli@0.5.0-rc.9
helm pull oci://core.campus.clusterdiali.me/harakiri/charts/harakiri \
  --version 0.5.0-rc.9
```

Use [Install on Kubernetes](https://sb.harakiri.io/#docs/install-kubernetes)
for a new standalone installation. The runtime chart remains
`opensandbox:0.2.2-harakiri.2`; this release changes the control plane and clients.
Verify exact OCI digests and npm integrity against the release artifact receipt.

**Migration 038 is a coordinated upgrade from rc.8.** Stop all pre-capacity
API/scheduler/worker writers, back up state, migrate, verify runtime inventory
and activate existing organizations before reopening mutations. Do not perform
a mixed old/new rolling upgrade or automatically roll back to pre-capacity rc.8.
Fresh organizations start enforced. Read the
[operator activation runbook](../operations/execution-capacity.md) first.

Upgrade API and SDK/CLI together: rc.9 does not silently treat an older API's
lifecycle status as successful readiness. After an explicit async create or
resume, call `waitForSandbox(id)` before submitting work. A successful probe is
a point-in-time observation, not application readiness or guaranteed latency.

## Evidence and Limits

Source verification passed 603 workspace checks (six optional integration checks
skipped), 157 required real-PostgreSQL capacity/fault checks and 17 browser
contracts. Six fresh native arm64 runtimes passed first writes and commands
without warm-up commands, recreation or mutation retries. Those source tests
used a local API against the isolated native provider/database; they are not
claimed as installation of published rc.9 artifacts.

See [execution readiness](../operations/execution-readiness.md),
[capacity fault acceptance](../operations/execution-capacity-fault-acceptance.md)
and [compatible rollback acceptance](../operations/execution-capacity-install-acceptance.md).
The release's subsequent delivery receipt records actual CI publication,
anonymous consumption and deployed-artifact acceptance.

Native amd64, restricted OpenShift runtime enforcement, HA/CSI recovery and
full encrypted Vault recovery are not certified by this release. The hosted lab
has no uptime SLA. Harbor storage headroom remains an operator follow-up;
successful publication alone would not establish durable registry capacity.
